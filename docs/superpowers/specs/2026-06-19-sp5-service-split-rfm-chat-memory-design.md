## 1. 目標與成功標準

**目標**：(A) 把過載的 `CustomerService` 拆出 `DashboardService`；(B) 加 RFM 客戶分群與端點；(C) 對話歷史落庫，並以「時序（最近 N 則）+ 語意向量（pgvector 相似歷史）」雙路注入 AI grounding context。

**成功標準**：
1. Dashboard 聚合（summary/reports/drilldown）移至 `DashboardService`，`DashboardController` 改用之，行為不變（SP2 dashboard 測試續綠）。
2. `GET /api/dashboard/rfm` 回每位客戶的 R/F/M 分數與分群標籤。
3. 對話訊息（user/assistant）落 `chat_messages`（含 embedding），每次 chat 後保存；下次提問時注入「最近 N 則 + 語意相似 K 則」到 context（且該記憶內容送 LLM 前過 PII 遮罩）。
4. `mvn -pl backend test` 全綠（含新測試）。

**非目標**：
- 不做對話記憶的前端 UI（後端能力備齊）。
- 不做跨客戶的全域對話檢索（記憶以 customer_id 為界）。
- 不拆 InsightService 的風險計算（風險邏輯已被 SP2 測試覆蓋且穩定；本 SP 聚焦 Dashboard 拆分與記憶）。

## 2. 元件設計

### 2.1 DashboardService（從 CustomerService 抽出）
- 搬移：`dashboardSummary()`、`dashboardReports()`、`drilldown(type,key)` 及其私有 helper。
- 依賴：`CustomerRepository`（或 CustomerService 的查詢方法）。優先直接用 repository，保持與原行為一致。
- `DashboardController` 改注入 `DashboardService`。
- `CustomerService` 保留 search/CRUD/addInteraction/findDetail/findAllWithDetail。
- **行為不變**：SP2 `DashboardIntegrationTest` 與 drilldown 既有行為續綠。

### 2.2 RfmService + 端點
- 計算（用現有 Interaction + Opportunity）：
  - R（Recency）：距今最後一次互動天數（越小越好）。
  - F（Frequency）：互動次數（可全期）。
  - M（Monetary）：商機金額合計（排除 CLOSED_LOST）。
- 評分：各維度對全體客戶做相對分級 1–5（用排序分位或門檻；資料量小用簡單門檻即可），R 反向（越近期分越高）。
- 分群標籤（依 R/F/M 高低）：如「冠軍客戶」「忠誠客戶」「具潛力」「需關注」「瀕危流失」等（規則可解釋）。
- `Dtos.RfmResponse(customerId, name, recencyDays, frequency, monetary, rScore, fScore, mScore, segment)`。
- 端點 `GET /api/dashboard/rfm`（authenticated）回 `List<RfmResponse>`。

### 2.3 對話記憶（時序 + 語意向量）
- `ChatMessage` entity + `chat_messages` 表（V7）：id, customer_id, role(USER/ASSISTANT), content, created_at, embedding vector(1024)。embedding 不映進 JPA（同 SP3 知識文件做法），用 JdbcTemplate。
- `ChatMessageRepository`（JPA）：時序查詢 `findTop6ByCustomerIdOrderByCreatedAtDesc`（最近 N，N 取 6＝約 3 輪）。
- `ChatMessageVectorRepository`（JdbcTemplate）：`save(customerId, role, content, vec)`、`searchTopK(customerId, queryVec, k)`（scoped by customer_id 的 cosine 檢索）。
- 保存：`InsightService.chat()` / `streamChat()` 在產生 answer 後，保存 user 訊息與 assistant 訊息（各 embed DOCUMENT 後存）。
- 注入：`buildAnswer`/grounding 組裝時，取「最近 N 則（時序，去除剛存入的本則）+ 語意相似 K 則（向量，排除重複）」組成「# 對話記憶」區塊，**過 PiiMasker 遮罩**後併入 prompt。
- 一致性：記憶寫入在 chat 流程內；若 embedding 失敗（fallback）仍存得了向量（deterministic），檢索照常。

## 3. 資料庫變更

Flyway `V7__add_chat_messages.sql`：
```sql
create table chat_messages (
    id bigint generated by default as identity primary key,
    customer_id bigint not null references customers(id),
    role varchar(20) not null,
    content text not null,
    embedding vector(1024),
    created_at timestamp with time zone not null
);
create index idx_chat_messages_customer_created on chat_messages(customer_id, created_at);
create index idx_chat_messages_embedding on chat_messages using hnsw (embedding vector_cosine_ops);
```

## 4. 測試

**單元**：
- `RfmServiceTest`（Mockito）：給定客戶集合，R/F/M 評分與分群標籤符合預期（含邊界：無互動、無商機）。
**整合（PostgresTestBase）**：
- `DashboardServiceIntegrationTest`：summary/reports/drilldown 經 DashboardService 回正確（或沿用 SP2 DashboardIntegrationTest 續綠即可，視拆分後是否需補）。
- `RfmEndpointIntegrationTest`：`GET /api/dashboard/rfm` 帶 token → 200 + 陣列含分數/分群欄位。
- `ChatMemoryIntegrationTest`：對同一客戶連續兩次 chat，第二次後 `chat_messages` 有 ≥4 筆（2 輪 × user+assistant）、且都有 embedding；驗證第二次呼叫的 grounding 有注入記憶（可由 ai_call_log answer 或記憶檢索方法間接驗證；或直接測 ChatMessageVectorRepository.searchTopK 回傳前一輪訊息）。

## 5. 風險與緩解

| 風險 | 緩解 |
|------|------|
| DashboardService 拆分改變聚合行為 | 純搬移；SP2 dashboard 測試護航；drilldown 邏輯整段搬不重寫 |
| 對話記憶讓 prompt 膨脹/成本上升 | 限最近 6 則 + 語意 3 則、各截斷長度；記憶過 PII 遮罩 |
| 每次 chat 多次 embedding 呼叫（user+assistant）成本 | 無金鑰走 deterministic（測試）；真 Voyage 僅每輪 2 次，可接受 |
| RFM 分位在資料量小時不穩 | 用簡單門檻而非嚴格分位；標註教學版 |
| 記憶寫入與 readOnly 交易衝突 | 保存走可寫交易（InsightService chat 方法非 readOnly 或拆出可寫方法/REQUIRES_NEW） |
